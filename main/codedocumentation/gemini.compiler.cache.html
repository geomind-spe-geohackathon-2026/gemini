gemini.compiler.cache

GraphCache: traced graphs by the structure of a module, retraced only when it changes.

The key of a graph is what the trace bakes in, for every module of the tree (a change anywhere below the root retraces): the root’s path, the module class and its declaration names and output formulas, the connections, constraints and ports of a plant, the values of non-numeric and structural parameters and the shapes of numeric ones, the tolerance and passes of a plant’s loops, the registered hooks and the module’s own fluid; and, once, whether outputs are enabled, the runtime precision, the inlet fluids and whether the graph is stepped. Numeric parameter values, constants and inputs are graph inputs, so changing them never retraces, and a graph holds no module (see Graph): every module with the same key, a copy of a plant with other numeric values for one, shares one graph. The cache stores graphs only: a module that cannot be traced is a root break graph (see rootbreak), remembered until the structure changes. Every graph is traced once and then merged by eliminate_common_subexpressions; GraphCache(optimize=False) keeps the traced graph as it is, for benchmarks and debugging.

graph_cache gives the one cache of the process, which the compiled executor uses. It keeps at most MAXSIZE graphs, the least recently used going first, so a long study of changing structures does not grow it: a graph refers to the declarations of the module it was traced from, and with them to that module, until it is dropped. A lock guards the table, so threads may share the cache, each with its own plants; two threads that miss on one key both trace it, and the last graph stays.
